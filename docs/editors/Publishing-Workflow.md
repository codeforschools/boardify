# Publishing Workflow

These instructions are the same whether for Policies or Regulations.


## Publishing Workflow

When you Update, Create or Delete a particular policy you are creating a new copy (called a branch) with your proposed changes, with the original left untouched.  The publishing workflow manages the state of those changes through the approval process.  There are three states to manage: Draft, Review, and Ready.

### Draft

All changes start in the `Draft` state.  A Draft is just that -- work in progress, which is anticipated to go through further changes and is not ready for review.  While anyone can comment on drafts, the changes are not yet ready for formal review or approval.

### Review

Once the changes are ready for review, you should put the policy into the `Review` state by clicking the drop-down button that says "Status: Draft" and switching it to "Status: Review".  This means that the document is ready for an official review and approval on the final document.  Changes can and do still happen in the `Review` state, and if necessary the document can be put back into the `Draft` state.  However, the purpose of the `Review` state is to indicate that the document is ready for others to formally review and approve.

### Ready

Once the changes are approved (usually in committee but also potentially over email/GitHub), the file should be changed to the `Ready` state.  This means that the document is in its final form for presentation to the Board.  Please note that whether or not a particular Policy/Regulation is actually placed on the Agenda is a decision for the Board Chair.  However, all documents that are `Ready` *could* be agendized at will -- that's the purpose of the `Ready` state..

> Side Note: Boardify uses GitHub Labels to manage this state internally.  Therefore, files viewed in GitHub directly will have the following names associated with each state:

  - `boardify/draft` in Purple
  - `boardify/review` in Yellow
  - `boardify/ready` in Green


## Publishing Changes

Again, it is not the Update/Create/Delete Editing Workflow that makes changes official, nor is it the Draft/Review/Ready Publishing Workflow.  What actually makes changes official is when they are **Published**.  And since only the Board can make this determination when voting on a particular set of changes, as a practical matter this means that only the Board Clerk should press the "Publish" button.[^1]  Authors should instead focus on maintaining the changes and state throughout the process.


[^1]: Technically Regulations *may* be Published at any time, but by convention they typically aren't until after the Board  has accepted them (usually via the consent agenda.)  So again, best to let the Clerk handle this.
